## 1. Зачем нужна автоматизация

Представьте, что нужно установить веб-сервер на десяти машинах. Можно зайти на каждую по SSH и вводить одни и те же команды вручную. Это долго, и на каждой машине легко сделать что-то по-своему.

**Автоматизация** означает, что действия записаны в файл, и компьютер выполняет их сам. Ansible делает именно это:

- запускается с одного управляющего узла (control node);
- подключается по SSH к управляемым узлам (managed nodes);
- выполняет задачи по описанию из файлов.

## 2. Что нужно перед установкой

Перед установкой проверьте три вещи:

1. **Управляющий узел.** Ansible устанавливается на Linux или macOS. На Windows его обычно запускают через WSL.
2. **Python на управляющем узле.** Ansible написан на Python, поэтому Python 3 должен быть установлен.
3. **Python и SSH на управляемых узлах.** Ansible подключается по SSH и запускает на сервере небольшие Python-скрипты. Поэтому на серверах должен быть Python 3 и доступ по SSH.

Проверить Python:

```bash
python3 --version
```

## 3. Установка Ansible

Есть несколько способов. Для учебной работы подойдут два.

### 3.1. Установка через apt (Ubuntu, Debian)

```bash
sudo apt update
sudo apt install -y ansible
```

Плюс: просто и быстро. Минус: версия может быть старее последней.

### 3.2. Установка через pipx

**pipx** устанавливает Python-программы в отдельное изолированное окружение. Это удобнее, чем ставить всё в систему.

```bash
sudo apt install -y pipx
pipx ensurepath
pipx install ansible
```

После `ensurepath` может потребоваться открыть новый терминал.

### 3.3. Проверка установки

```bash
ansible --version
```

В выводе будет версия Ansible, версия Python и путь к конфигурационному файлу. Если команда работает, установка прошла успешно.

Если команда `ansible` не найдена, проверьте, что установка прошла, и что путь к программам попал в переменную `PATH`.

## 4. Подготовка управляемых узлов

Чтобы Ansible мог работать с сервером, нужно:

- иметь SSH-доступ по паролю или ключу;
- иметь пользователя, который может выполнять административные действия через `sudo`;
- иметь Python 3 на сервере.

Проверить, что сервер доступен, можно командой:

```bash
ssh {ПОЛЬЗОВАТЕЛЬ_SSH_СЕРВЕРА}@{IP_АДРЕС_SSH_СЕРВЕРА} "python3 --version"
```

Если команда вывела версию Python, сервер готов к работе с Ansible.

## 5. Файл настроек ansible.cfg

Ansible можно настроить через файл `ansible.cfg`. Его кладут в папку проекта.

```ini
[defaults]
inventory = ./inventory.ini
remote_user = admin
host_key_checking = True
```

Что здесь что значит:

- `inventory` — путь к файлу инвентаризации. Тогда `-i` в командах не нужен.
- `remote_user` — пользователь для подключения по умолчанию.
- `host_key_checking` — проверять отпечатки серверов (см. тему про аутентификацию). Значение `True` — безопаснее.

Посмотреть, какие настройки сейчас действуют:

```bash
ansible-config dump --only-changed
```

Если `ansible.cfg` лежит в текущей папке, Ansible использует его автоматически.

## 6. Ad-hoc команды

**Ad-hoc команда** — это одиночная команда Ansible, которая выполняется без плейбука. Она удобна для быстрых проверок.

Общий вид:

```bash
ansible <группа_или_сервер> -i inventory.ini -m <модуль> -a "<аргументы>"
```

Что означают части:

- `<группа_или_сервер>` — кому выполнить команду: имя сервера, группа или `all`;
- `-i` — путь к файлу инвентаризации;
- `-m` — модуль (готовое действие);
- `-a` — аргументы модуля.

### 6.1. Проверка связи

```bash
ansible all -i inventory.ini -m ping
```

Модуль `ping` не посылает ICMP-пакет. Он проверяет, что Ansible может подключиться к серверу и запустить на нём Python. Если ответ `pong`, всё в порядке.

### 6.2. Выполнение команды на сервере

```bash
ansible webservers -i inventory.ini -m command -a "uptime"
```

Модуль `command` выполняет обычную команду. Он не понимает shell-конструкции (например, `|` или `>`). Для них есть модуль `shell`, но его лучше использовать только тогда, когда без него не обойтись.

### 6.3. Команды с правами администратора

Установка пакетов и управление службами требуют прав администратора. Для этого есть ключ `-b` (become):

```bash
ansible webservers -i inventory.ini -b -m apt -a "name=nginx state=present"
```

Если сервер просит пароль `sudo`, добавьте ключ `-K`. Ansible спросит его один раз при запуске:

```bash
ansible webservers -i inventory.ini -b -K -m apt -a "name=nginx state=present"
```

### 6.4. Полезные модули для ad-hoc

|Модуль|Для чего|
|---|---|
|`ping`|проверка связи|
|`command`|выполнение простой команды|
|`apt`|установка и удаление пакетов (Debian, Ubuntu)|
|`service`|запуск, остановка и автозапуск служб|
|`copy`|копирование файла на сервер|

Подробнее о модуле можно прочитать командой:

```bash
ansible-doc ansible.builtin.apt
```

## 7. Плейбук: основной способ автоматизации

Ad-hoc команды подходят для одного действия. Если действий несколько, их записывают в **плейбук**.

Пример плейбука `site.yml`:

```yaml
---
- name: Установка и настройка веб-сервера
  hosts: webservers
  become: true

  tasks:
    - name: Установить nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Создать страницу сайта
      ansible.builtin.copy:
        dest: /var/www/html/index.html
        content: "<h1>Сервер настроен через Ansible</h1>\n"

    - name: Запустить nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

Что здесь что значит:

- `hosts: webservers` — на какую группу применяется сценарий;
- `become: true` — выполнять задачи с правами администратора;
- каждая задача имеет понятное `name`, которое видно в выводе;
- `ansible.builtin.apt`, `ansible.builtin.copy`, `ansible.builtin.service` — модули, которые выполняют действия.

### 7.1. Запуск плейбука

```bash
ansible-playbook -i inventory.ini -K site.yml
```

Ключ `-K` спрашивает пароль `sudo`, если он нужен.

### 7.2. Проверка без изменений

Перед реальным запуском полезно проверить, что изменится:

```bash
ansible-playbook -i inventory.ini site.yml --check --diff
```

- `--check` — ничего не менять, только показать, что было бы сделано;
- `--diff` — показать различия в файлах.

Эта проверка не всегда точна. Некоторые задачи в режиме `--check` не выполняются, поэтому результат может немного отличаться от реального запуска.

### 7.3. Подробный вывод

Чтобы увидеть больше информации, добавьте `-v`:

```bash
ansible-playbook -i inventory.ini site.yml -v
```

Можно добавить до `-vvv`. Чем больше букв `v`, тем подробнее вывод.

## 8. Как читать вывод Ansible

В конце каждого запуска выводится **PLAY RECAP** — итоговая таблица по серверам:

```text
PLAY RECAP
web1  : ok=4  changed=2  unreachable=0  failed=0  skipped=0
web2  : ok=4  changed=2  unreachable=0  failed=0  skipped=0
```

Что означают поля:

- **ok** — задач выполнено успешно, включая те, которые ничего не меняли;
- **changed** — задач, которые реально что-то изменили;
- **unreachable** — серверы, к которым не удалось подключиться;
- **failed** — задачи, которые завершились с ошибкой;
- **skipped** — пропущенные задачи (например, по условию).

Цвета в выводе тоже важны:

- **зелёный** — без изменений;
- **жёлтый** — было изменение;
- **красный** — ошибка.

## 9. Идемпотентность

**Идемпотентность** — это свойство, при котором повторный запуск не ломает систему и не делает лишних изменений.

Пример: при первом запуске `nginx` устанавливается, и `changed=1`. При втором запуске Ansible видит, что пакет уже есть, и пишет `ok`, а не `changed`.

Это важно, потому что плейбук можно безопасно запускать много раз. Если во втором запуске видно `changed`, значит, что-то изменилось с прошлого раза: сервер сменил конфигурацию или плейбук был изменён.

## 10. Типичные ошибки

- **`ansible: command not found`.** Ansible не установлен или не попал в `PATH`. Проверьте установку и активацию виртуального окружения python (`source venv/bin/activate`).
- **`UNREACHABLE`.** Нет связи с сервером. Проверьте адрес, пользователя и ключ (см. тему про аутентификацию).
- **`Missing sudo password`.** Нужен пароль `sudo`. Добавьте `-K`.
- **`Permission denied`.** Пользователь не имеет прав. Добавьте `-b` или `become: true` и проверьте права пользователя.
- **`Unable to find python interpreter`.** На управляемом сервере нет Python 3. Установите его на сервер.
- **Ошибка в YAML.** Чаще всего это табуляция или неверные отступы (см. тему про YAML).
