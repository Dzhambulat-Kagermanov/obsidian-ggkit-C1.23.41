## 1. Файл инвентаризации (inventory)

### 1.1. Что такое инвентарь

**Инвентарь** — это файл со списком управляемых серверов. Ansible читает его, чтобы узнать:
- к каким машинам подключаться;
- какие серверы объединены в группы;
- какие переменные действуют на серверы и группы.

Если файл не указан, Ansible ищет инвентарь по умолчанию (`/etc/ansible/hosts`). Чаще инвентарь передают явно через ключ `-i`:

```bash
ansible all -i inventory.ini -m ping
```

Путь к инвентарю можно записать в файл настроек `ansible.cfg`, тогда `-i` не нужен:

```ini
[defaults]
inventory = ./inventory.ini
```

### 1.2. Два формата инвентаря

Инвентарь может быть в двух форматах:
- **INI** — простой формат из строк;
- **YAML** — формат с отступами.

Оба формата описывают одно и то же. Выберите один и не смешивайте их в одном файле. В этом конспекте сначала разбирается INI, потому что его проще читать.

### 1.3. Формат INI

```ini
[webservers]
web1 ansible_host=192.168.1.10
web2 ansible_host=192.168.1.11

[dbservers]
db1 ansible_host=192.168.1.20

[all:vars]
ansible_user=admin
```

Что здесь что значит:
- `[webservers]` — название группы. Все строки под ним относятся к этой группе.
- `web1` — имя сервера. Это имя для Ansible, оно может отличаться от реального имени машины.
- `ansible_host=...` — адрес сервера (IP или доменное имя). Записывается в ту же строку, что и имя.
- `[all:vars]` — переменные, которые действуют на все серверы.
- `ansible_user=admin` — пользователь, под которым Ansible заходит на серверы.

Правила записи INI:
- одна строка — один сервер;
- название группы пишется в квадратных скобках `[ ]`;
- пробелы между именем сервера и переменными — обычные;
- пробелы вокруг знака `=` не ставятся: `ansible_host=192.168.1.10`.

### 1.4. Группы

Группы нужны, чтобы применять задачи сразу к нескольким серверам.

Один сервер может входить в несколько групп. Например, `web1` — и веб-сервер, и сервер для тестов:

```ini
[webservers]
web1 ansible_host=192.168.1.10

[test]
web1
```

Группа `all` содержит **все** серверы из инвентаря, даже если они не записаны в явную группу.

Группы можно вкладывать друг в друга. Для этого используется `:children`:

```ini
[frontend]
web1 ansible_host=192.168.1.10
web2 ansible_host=192.168.1.11

[backend]
db1 ansible_host=192.168.1.20

[production:children]
frontend
backend
```

Здесь группа `production` включает в себя `frontend` и `backend`. Если задача применяется к `production`, она попадёт на все четыре сервера.

### 1.5. Зачем отдельно имя сервера и `ansible_host`

Можно написать в инвентаре только адрес:

```ini
[dbservers]
192.168.1.20
```

Ansible подключится к `192.168.1.20`, так что такой файл тоже работает. Но тогда адрес одновременно становится и именем сервера, и его адресом.

Обычно пишут имя и отдельно `ansible_host`:

```ini
[dbservers]
db1 ansible_host=192.168.1.20
```

Здесь `db1` — это **имя для Ansible**, а `ansible_host=192.168.1.20` — это **адрес, куда подключаться**. Они разделены специально.

Что это даёт:
- **Понятное имя.** `db1` сразу говорит, что это база данных. Цифры `192.168.1.20` ничего не говорят о роли сервера.
- **Удобные команды.** Вместо адреса можно писать имя:
  ```bash
  ansible db1 -i inventory.ini -m ping
  ansible dbservers -i inventory.ini -m ping
  ```
- **Удобные плейбуки.** В плейбуке пишется `hosts: dbservers`, а не список адресов.
- **Лёгкая смена адреса.** Если сервер получил новый IP, меняется одна строка в инвентаре. Плейбуки и команды трогать не нужно.
- **Доменные имена.** Если у сервера есть DNS-имя, можно указать его:
  ```ini
  db1 ansible_host=db1.example.local
  ```
- **Свои настройки для одного сервера.** Пользователь, порт или ключ можно задать в той же строке, не затрагивая остальные серверы.

Если имя сервера совпадает с его реальным DNS-именем или адресом, `ansible_host` можно не писать. Для учебного и рабочего инвентаря удобнее всегда указывать имя и `ansible_host` явно: так файл яснее и проще менять.

### 1.6. Переменные в инвентаре

Переменные можно задать на трёх уровнях.

**Для всех серверов** — в группе `[all:vars]`:

```ini
[all:vars]
ansible_user=admin
```

**Для одной группы** — в группе `[имя_группы:vars]`:

```ini
[dbservers:vars]
ansible_user=dbadmin
```

**Для одного сервера** — прямо в его строке:

```ini
db1 ansible_host=192.168.1.20 ansible_user=root
```

Если одна и та же переменная задана в нескольких местах, побеждает более конкретное значение: сервер важнее группы, группа важнее общих настроек.

Основные переменные подключения (на этом этапе достаточно трёх):

| Переменная | Что означает |
|---|---|
| `ansible_host` | адрес сервера |
| `ansible_user` | пользователь, под которым заходит Ansible |
| `ansible_password` | пароль этого пользователя (для входа по паролю) |

> Пароль в открытом виде в файле — плохая практика. Здесь он показан только для понимания. Как правильно защищать пароли, разберём в отдельной теме.

### 1.7. Формат YAML

Тот же инвентарь в YAML:

```yaml
all:
  vars:
    ansible_user: admin
  children:
    webservers:
      hosts:
        web1:
          ansible_host: 192.168.1.10
        web2:
          ansible_host: 192.168.1.11
    dbservers:
      hosts:
        db1:
          ansible_host: 192.168.1.20
```

Сравнение форматов:

| Что нужно | INI | YAML |
|---|---|---|
| Сервер в группе | строка под `[группа]` | ключ внутри `hosts:` |
| Переменные группы | `[группа:vars]` | ключ `vars:` внутри группы |
| Вложенные группы | `[группа:children]` | ключ `children:` |
| Читаемость | проще для коротких файлов | удобнее для больших проектов |

### 1.8. Проверка инвентаря

Показать, что Ansible видит в инвентаре, в виде списка:

```bash
ansible-inventory -i inventory.ini --list
```

Показать группы в виде дерева:

```bash
ansible-inventory -i inventory.ini --graph
```

Вывести только имена серверов:

```bash
ansible all -i inventory.ini --list-hosts
```

Проверить, что серверы доступны:

```bash
ansible all -i inventory.ini -m ping
```

Команда `--graph` удобна тем, что сразу видно, какой сервер в какую группу попал.

### 1.9. Частые ошибки в инвентаре

- **Опечатка в имени группы.** `[webserver]` и `[webservers]` — это разные группы. Проверяйте имя в плейбуке и в инвентаре.
- **Пробелы вокруг `=`.** Пишите `ansible_user=admin`, а не `ansible_user = admin`.
- **Смешаны форматы.** INI-строки внутри YAML-файла, или наоборот, не работают.
- **Неверный адрес.** Если `ansible_host` указан с ошибкой, команда `ping` вернёт ошибку подключения.
- **Сервер не в той группе.** Проверьте через `--graph`.

## 2. Аутентификация

### 2.1. Что такое аутентификация

**Аутентификация** — это проверка, что вы тот, за кого себя выдаёте. Когда Ansible подключается к серверу по SSH, сервер должен понять, что Ansible действительно может зайти под указанным пользователем.

Для этого есть два основных способа:
- **пароль**;
- **ключевая пара**.

### 2.2. Аутентификация по паролю

Самый простой способ:
1. В инвентаре указываются `ansible_user` и `ansible_password`.
2. Ansible заходит на сервер под этим пользователем и вводит пароль автоматически.

Пример:

```ini
[webservers]
web1 ansible_host=192.168.1.10 ansible_user=admin ansible_password=secret123
```

Чтобы Ansible мог работать с паролем, на управляющем узле должна быть установлена утилита `sshpass`:

```bash
sudo apt install sshpass
```

Обычный вход по паролю вручную выглядит так (система спросит пароль):

```bash
ssh admin@192.168.1.10
```

При первом подключении к новому серверу SSH спросит, доверяете ли вы его отпечатку (fingerprint). Ответ `yes` добавит сервер в файл `known_hosts`. Это нормальное поведение, но отвечать нужно осознанно: отпечаток проверяется один раз.

Минусы парольного входа:
- пароль нужно где-то хранить;
- пароль можно угадать или перехватить;
- сложнее менять пароли на многих серверах сразу.

### 2.3. Аутентификация по ключевой паре

Второй способ — **ключевая пара**. Она состоит из двух файлов:
- **приватный ключ** — хранится только у вас и никуда не передаётся;
- **публичный ключ** — его копируют на сервер.

Сервер проверяет, что вы владеете приватным ключом, и пускает без пароля. Сам приватный ключ по сети не передаётся.

Как это работает по шагам:
1. Вы создаёте ключевую пару на управляющем узле.
2. Публичный ключ добавляется на сервер в файл `~/.ssh/authorized_keys` пользователя.
3. При входе сервер просит доказать владение приватным ключом.
4. Ключ подтверждается, и вход разрешён.

#### Создание ключевой пары

```bash
ssh-keygen -t ed25519
```

По умолчанию появятся два файла в папке `~/.ssh/`:
- `id_ed25519` — приватный ключ;
- `id_ed25519.pub` — публичный ключ.

Команда спросит пароль для ключа (passphrase). Его можно оставить пустым, но с паролем безопаснее: даже если файл утечёт, без пароля им не воспользоваться. Пароль на ключ обычно вводится один раз благодаря ssh-agent (см. раздел 3).

#### Копирование публичного ключа на сервер

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub admin@192.168.1.10
```

Команда добавит публичный ключ в `authorized_keys` на сервере. Если `ssh-copy-id` недоступен, можно сделать то же вручную, но это сложнее и легко ошибиться.

После копирования можно зайти без пароля:

```bash
ssh -i ~/.ssh/id_ed25519 admin@192.168.1.10
```

#### Указание ключа в инвентаре

В INI-файле вместо пароля указывается путь к приватному ключу:

```ini
[webservers]
web1 ansible_host=192.168.1.10 ansible_user=admin ansible_ssh_private_key_file=~/.ssh/id_ed25519
```

Переменная `ansible_ssh_private_key_file` говорит Ansible, каким ключом пользоваться. Её можно записать и в `[all:vars]`, если все серверы используют один ключ.

#### Права на приватный ключ

SSH не будет использовать ключ, если его могут читать другие пользователи:

```bash
chmod 600 ~/.ssh/id_ed25519
```

### 2.4. Сравнение способов входа

| | Пароль | Ключевая пара |
|---|---|---|
| Что указывается в инвентаре | `ansible_password` | `ansible_ssh_private_key_file` |
| Что хранится у вас | пароль | приватный ключ |
| Безопасность | ниже | выше |
| Нужна утилита `sshpass` | да | нет |
| Удобство на многих серверах | сложнее менять | один ключ на все серверы |

### 2.5. Частые ошибки при подключении

- **`Permission denied (publickey,password)`.** Сервер не принял ни ключ, ни пароль. Проверьте имя пользователя, пароль и то, что публичный ключ добавлен именно этому пользователю.
- **`UNREACHABLE`.** Ansible не смог подключиться по сети. Проверьте адрес, порт и доступность сервера.
- **`sshpass: command not found`.** Не установлена утилита для парольного входа.
- **`WARNING: UNPROTECTED PRIVATE KEY FILE`.** Слишком широкие права на приватный ключ. Выполните `chmod 600`.
- **`Host key verification failed`.** Отпечаток сервера не совпадает с записанным в `known_hosts`. Это может означать, что сервер переустановили или подменили. Не игнорируйте это сообщение без проверки.

## 3. Хранилище ключей

Здесь речь о том, где на управляющем узле лежат SSH-ключи и как с ними безопасно работать.

### 3.1. Папка `~/.ssh`

```text
~/.ssh/
├── id_ed25519        приватный ключ (секрет)
├── id_ed25519.pub    публичный ключ
├── known_hosts       список серверов, которым вы доверяете
└── config            настройки подключений
```

Что хранится в каждом файле:
- **`id_ed25519`** — приватный ключ. Это главный секрет. Никому не передаётся.
- **`id_ed25519.pub`** — публичный ключ. Его можно показывать и копировать на серверы.
- **`known_hosts`** — записи о серверах, отпечатки которых вы уже проверили.
- **`config`** — файл с настройками подключений (см. раздел 3.4).

На самом сервере похожую роль играет файл `~/.ssh/authorized_keys`: в нём лежат публичные ключи, которым разрешён вход.

### 3.2. Права доступа

- Приватный ключ — `600` (читать и менять может только владелец).
- Папка `~/.ssh` — `700`.

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
```

Публичный ключ можно оставить с обычными правами: его нельзя использовать для входа, он только подтверждает ключ.

### 3.3. Правила безопасного хранения

- Приватный ключ никому не передаётся и не публикуется.
- Приватный ключ не кладут в Git-репозиторий и не отправляют в мессенджеры.
- Для разных задач и разных людей лучше использовать разные ключи.
- Если ключ скомпрометирован, его удаляют с серверов и создают новый.

### 3.4. Файл `~/.ssh/config`

Вместо того чтобы писать одни и те же настройки в инвентаре, их можно описать в файле `~/.ssh/config`:

```text
Host db1
    HostName 192.168.1.20
    User admin
    IdentityFile ~/.ssh/id_ed25519
```

Теперь команда `ssh db1` сама подставит адрес, пользователя и ключ. Ansible тоже учитывает эти настройки. Для учебного проекта удобнее держать всё в инвентаре, а `config` использовать как дополнение.

### 3.5. Агент ключей (ssh-agent)

**ssh-agent** хранит расшифрованный ключ в памяти. Если на ключ стоит пароль (passphrase), он вводится один раз, а не при каждом подключении.

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
```

Посмотреть, какие ключи загружены:

```bash
ssh-add -l
```

Агент работает, пока открыт текущий сеанс терминала. После перезагрузки ключ нужно добавить снова.
