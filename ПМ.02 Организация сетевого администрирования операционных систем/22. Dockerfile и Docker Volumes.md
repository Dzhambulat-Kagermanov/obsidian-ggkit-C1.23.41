## 1. Создание собственных образов Docker

### 1.1. Назначение Dockerfile

<mark style="background:#fff88f">**Dockerfile** — текстовый файл, содержащий инструкции для создания образа. С помощью этого файла можно создать свой образ.</mark>

<mark style="background:#fff88f">Готовые образы из Docker Hub подходят не для всех задач. Например, для запуска собственного веб-приложения может потребоваться установка дополнительных пакетов, копирование файлов и настройка рабочей директории.</mark>

Dockerfile позволяет описать эти действия в одном файле.

**Принцип работы:**

1. Создание файла `Dockerfile`.
    
2. Добавление инструкций для подготовки образа.
    
3. Сборка образа с помощью `docker build`.
    
4. Создание контейнера на основе полученного образа.
    

### **1.2. Структура Dockerfile**

Dockerfile содержит последовательность инструкций. Каждая инструкция определяет действие при сборке образа или настройку будущего контейнера.

Пример:

```
FROM nginx:stable
COPY index.html /usr/share/nginx/html/index.html
```

Здесь:

- `FROM` — выбор базового образа.
    
- `COPY` — копирование файла в образ.
    

В результате получается собственный образ Nginx с заранее подготовленной HTML-страницей.

## **2. Основные инструкции Dockerfile**

### **2.1. Базовый образ —** `FROM`

`FROM` — инструкция выбора образа, на основе которого создаётся новый образ.

```
FROM ubuntu:24.04
```

В данном случае новый образ будет содержать пользовательское окружение Ubuntu 24.04.

Для веб-сервера:

```
FROM nginx:stable
```

Обычно `FROM` является первой инструкцией Dockerfile.

### **2.2. Выполнение команд —** `RUN`

`RUN` — инструкция выполнения команды во время сборки образа.

Пример:

```
FROM ubuntu:24.04
RUN apt update
```

Установка пакета:

```
FROM ubuntu:24.04
RUN apt update && apt install -y curl
```

При сборке Docker выполнит команды и сохранит результат в образе.

**Особенность:** `RUN` выполняется при сборке образа, а не при каждом запуске контейнера.

### **2.3. Копирование файлов —** `COPY`

`COPY` — инструкция копирования файлов и каталогов из контекста сборки внутрь образа.

Синтаксис:

```
COPY ИСТОЧНИК НАЗНАЧЕНИЕ
```

Пример:

```
COPY index.html /usr/share/nginx/html/index.html
```

Файл `index.html` копируется в каталог веб-сервера Nginx.

**Контекст сборки** — каталог с файлами, которые Docker получает для сборки образа. Обычно это текущий каталог, указанный точкой `.` в команде `docker build`.

### **2.4. Рабочая директория —** `WORKDIR`

`WORKDIR` — инструкция установки рабочей директории для последующих инструкций Dockerfile и запускаемых процессов.

```
WORKDIR /app
```

После этого относительные пути в инструкциях будут отсчитываться от `/app`.

Пример:

```
FROM ubuntu:24.04
WORKDIR /app
COPY hello.txt .
```

Файл `hello.txt` будет скопирован в `/app/hello.txt`.

### **2.5. Команда запуска —** `CMD`

`CMD` — инструкция определения команды по умолчанию при запуске контейнера.

Пример:

```
FROM ubuntu:24.04
CMD ["echo", "Hello Docker"]
```

После запуска контейнер выведет сообщение и завершит работу.

Другой пример:

```
CMD ["sleep", "3600"]
```

Контейнер запустит процесс `sleep`, который будет работать в течение 3600 секунд.

Команду `CMD` можно переопределить при выполнении `docker run`.

### **2.6. Документирование порта —** `EXPOSE`

`EXPOSE` — инструкция указания порта, который предполагается использовать приложением внутри контейнера.

```
EXPOSE 80
```

Эта инструкция **не публикует порт на хосте**.

Для предоставления доступа через хост по-прежнему используется параметр `-p` команды `docker run`.

Например:

```
sudo docker run -d -p 8080:80 my-nginx
```

## **3. Сборка собственного Docker-образа**

### **3.1. Подготовка проекта**

Создание каталога:

```
mkdir docker-site
```

Переход в каталог:

```
cd docker-site
```

Создание HTML-файла:

```
nano index.html
```

Содержимое:

```
<!DOCTYPE html>
<html>
<head>
    <meta charset="UTF-8">
    <title>Docker</title>
</head>
<body>
    <h1>Мой первый Docker-образ</h1>
</body>
</html>
```

Создание Dockerfile:

```
nano Dockerfile
```

Содержимое:

```
FROM nginx:stable
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
```

### **3.2. Сборка образа —** `docker build`

`docker build` — команда создания образа на основе Dockerfile.

```
sudo docker build -t my-nginx:1.0 .
```

Разбор параметров:

- `build` — запуск процесса сборки.
    
- `-t` — назначение имени и тега образа.
    
- `my-nginx` — имя создаваемого образа.
    
- `1.0` — тег образа.
    
- `.` — текущий каталог как контекст сборки.
    

Во время сборки Docker последовательно обрабатывает инструкции Dockerfile.

### **3.3. Проверка образа**

```
sudo docker images
```

В списке должен появиться образ `my-nginx` с тегом `1.0`.

### **3.4. Запуск контейнера**

```
sudo docker run -d --name my-site -p 8080:80 my-nginx:1.0
```

Проверка:

```
curl http://localhost:8080
```

В результате должна отображаться HTML-страница, добавленная в образ.

## **4. Слои Docker-образа**

**Слой образа (Image Layer)** — часть файловой системы образа, содержащая изменения, полученные на определённом этапе сборки.

Docker использует слои для повторного использования данных и ускорения сборки.

Например:

```
FROM ubuntu:24.04
RUN apt update
RUN apt install -y curl
COPY hello.txt /app/hello.txt
```

Инструкции, изменяющие файловую систему, формируют слои образа.

При повторной сборке Docker может использовать ранее созданные слои из кэша, если соответствующие данные и инструкции не изменились.

### **4.1. Просмотр истории образа**

```
sudo docker history my-nginx:1.0
```

Команда отображает историю формирования образа, включая инструкции и размеры слоёв.

### **4.2. Изменение образа**

После изменения `index.html` необходимо повторно собрать образ:

```
sudo docker build -t my-nginx:1.1 .
```

Создаётся новая версия образа с тегом `1.1`.

**Важно:** изменение Dockerfile или исходных файлов не обновляет автоматически уже запущенный контейнер. Для применения нового образа необходимо создать новый контейнер.

## **5. Хранение данных в контейнерах**

### **5.1. Записываемый слой контейнера**

При создании контейнера Docker добавляет поверх слоёв образа отдельный **записываемый слой**.

В него попадают изменения, выполняемые во время работы контейнера:

- создание файлов;
    
- изменение существующих файлов;
    
- удаление файлов;
    
- изменение данных приложения.
    

При удалении контейнера его записываемый слой также удаляется.

Поэтому хранить важные данные только внутри файловой системы контейнера нежелательно.

Например, если база данных хранит свои файлы исключительно в записываемом слое контейнера, удаление контейнера приведёт к потере этих данных.

### **5.2. Постоянное хранение данных**

**Постоянное хранение данных** — размещение файлов вне записываемого слоя контейнера, чтобы они сохранялись при его удалении и повторном создании.

В Docker для этого используются:

- **Volumes** — тома, которыми управляет Docker.
    
- **Bind Mounts** — подключение файлов или каталогов хостовой системы.
    

## **6. Docker Volumes**

### **6.1. Понятие Volume**

**Docker Volume** — область хранения данных, управляемая Docker и подключаемая к контейнерам.

Данные тома сохраняются независимо от жизненного цикла контейнера.

Например, можно удалить контейнер с базой данных и создать новый, подключив тот же том. Файлы базы данных останутся доступными.

### **6.2. Создание тома —** `volume create`

```
sudo docker volume create site-data
```

Команда создаёт том с именем `site-data`.

### **6.3. Просмотр томов —** `volume ls`

```
sudo docker volume ls
```

Команда отображает существующие Docker Volumes.

### **6.4. Подключение тома —** `-v`

Для подключения тома используется параметр `-v`.

Синтаксис:

```
-v ИМЯ_ТОМА:ПУТЬ_В_КОНТЕЙНЕРЕ
```

Пример:

```
-v site-data:/data
```

Здесь:

- `site-data` — имя Docker Volume.
    
- `/data` — каталог внутри контейнера.
    

Файлы, записанные контейнером в `/data`, будут храниться в томе `site-data`.

### **6.5. Пример постоянного хранения файлов**

Создание контейнера с подключённым томом:

```
sudo docker run -it --name data-test -v site-data:/data ubuntu:24.04 bash
```

Создание файла внутри контейнера:

```
echo "Hello Volume" > /data/test.txt
```

Проверка содержимого:

```
cat /data/test.txt
```

Выход:

```
exit
```

Удаление контейнера:

```
sudo docker rm data-test
```

Создание нового контейнера с тем же томом:

```
sudo docker run -it --name data-test-2 -v site-data:/data ubuntu:24.04 bash
```

Проверка файла:

```
cat /data/test.txt
```

Файл сохранится, поскольку он размещён в Docker Volume, а не в записываемом слое удалённого контейнера.

### **6.6. Просмотр информации о томе —** `volume inspect`

```
sudo docker volume inspect site-data
```

Команда позволяет получить информацию о томе, включая его имя, драйвер и расположение данных на хосте.

### **6.7. Удаление тома —** `volume rm`

```
sudo docker volume rm site-data
```

Удаление возможно, если том не используется существующими контейнерами.

**Важно:** удаление тома приводит к удалению хранящихся в нём данных.

## **7. Bind Mounts**

### **7.1. Понятие Bind Mount**

**Bind Mount** — подключение существующего файла или каталога хостовой системы внутрь контейнера.

В отличие от Docker Volume, расположение данных определяется администратором.

Например, каталог `/home/user/site` можно подключить к каталогу `/usr/share/nginx/html` внутри контейнера Nginx.

### **7.2. Подключение каталога хоста**

Создание каталога:

```
mkdir -p ~/my-site
```

Создание HTML-файла:

```
echo "<h1>Hello Bind Mount</h1>" > ~/my-site/index.html
```

Запуск контейнера:

```
sudo docker run -d --name bind-site -p 8081:80 -v "$(pwd)/my-site:/usr/share/nginx/html:ro" nginx:stable
```

В этом примере предполагается, что текущий каталог — домашний каталог пользователя, где создан `my-site`.

Разбор:

- `$(pwd)/my-site` — абсолютный путь к каталогу на хосте.
    
- `/usr/share/nginx/html` — каталог внутри контейнера.
    
- `ro` — подключение только для чтения.
    

Проверка:

```
curl http://localhost:8081
```

При изменении HTML-файла на хосте Nginx сможет использовать обновлённое содержимое без пересборки образа.

## **8. Отличия Docker Volume и Bind Mount**

|Характеристика|Docker Volume|Bind Mount|
|---|---|---|
|Управление|Docker|Администратор|
|Расположение|Определяет Docker|Задаётся вручную|
|Основное назначение|Постоянные данные приложений|Подключение файлов хоста|
|Создание|`docker volume create` или автоматически|Использование пути хоста|
|Типичный пример|Данные PostgreSQL|Исходный код и конфигурации|

**Docker Volumes** обычно удобнее для постоянных данных приложений.

**Bind Mounts** удобны, когда необходимо работать с файлами хоста напрямую, например при разработке веб-приложения.
