## 1. Назначение Dockerfile

<mark style="background:#fff88f">**Dockerfile** — текстовый файл, содержащий инструкции для создания образа. С помощью этого файла можно создать свой образ.</mark>

<mark style="background:#fff88f">Готовые образы из Docker Hub подходят не для всех задач. Например, для запуска собственного веб-приложения может потребоваться установка дополнительных пакетов, копирование файлов и настройка рабочей директории.</mark>

## 2. Основные инструкции Dockerfile

### 2.1. Базовый образ — `FROM`

<mark style="background:#fff88f">`FROM` — инструкция выбора образа, на основе которого создаётся новый образ.</mark>

```Dockerfile
FROM ubuntu:24.04
```

<mark style="background:#fff88f">Обычно `FROM` является первой инструкцией Dockerfile.</mark>

### 2.2. Выполнение команд — `RUN`

<mark style="background:#fff88f">`RUN` — инструкция выполнения команды во время сборки образа.</mark>

<mark style="background:#fff88f">Пример:</mark>

```Dockerfile
FROM ubuntu:24.04
RUN apt update
```

>[!TIP] Особенность RUN
><mark style="background:#fff88f">`RUN` выполняется при сборке образа, а не при каждом запуске контейнера.</mark>

### 2.3. Копирование файлов — `COPY`

<mark style="background:#fff88f">`COPY` — инструкция копирования файлов и каталогов из контекста сборки внутрь образа.</mark>

<mark style="background:#fff88f">Синтаксис:</mark>

```Dockerfile
COPY ХОСТОВЫЙ_ПУТЬ КОНТЕЙНЕРНЫЙ_ПУТЬ
```

<mark style="background:#fff88f">Пример:</mark>

```Dockerfile
COPY ./index.html /usr/share/nginx/html/index.html
```

### 2.4. Рабочая директория — `WORKDIR`

<mark style="background:#fff88f">`WORKDIR` — инструкция установки рабочей директории для последующих инструкций Dockerfile и запускаемых процессов. Похожа на `cd` для перехода в директорию. Если указанной директории в контейнере ещё нет, Docker создаст её автоматически.</mark>

```Dockerfile
WORKDIR /app
```

<mark style="background:#fff88f">После этого относительные пути в инструкциях будут отсчитываться от `/app`. Пример:</mark>

```Dockerfile
FROM ubuntu:24.04
WORKDIR /app
COPY hello.txt .
```

<mark style="background:#fff88f">Файл `hello.txt` будет скопирован в `/app/hello.txt`.</mark>

### 2.5. Команда запуска — `CMD`

<mark style="background:#fff88f">`CMD` — инструкция определения команды по умолчанию при запуске контейнера.</mark>

<mark style="background:#fff88f">Пример:</mark>

```Dockerfile
FROM ubuntu:24.04
CMD ["echo", "Hello Docker"]
```

<mark style="background:#fff88f">После запуска контейнер выведет сообщение и завершит работу.</mark>

### 2.6. Документирование порта — `EXPOSE`

<mark style="background:#fff88f">`EXPOSE` — инструкция указания порта, который предполагается использовать приложением внутри контейнера.</mark>

```Dockerfile
EXPOSE 80
```

## 3. Сборка собственного Docker-образа

### 3.1. Подготовка проекта

Создание каталога:

```bash
mkdir docker-site
```

Переход в каталог:

```bash
cd docker-site
```

Создание HTML-файла:

```bash
nano index.html
```

Содержимое:

```html
<!DOCTYPE html>
<html>
<head>
    <meta charset="UTF-8">
    <title>Docker</title>
</head>
<body>
    <h1>Мой первый Docker-образ</h1>
</body>
</html>
```

Создание Dockerfile:

```bash
nano Dockerfile
```

Содержимое:

```Dockerfile
FROM nginx:stable
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
```

### 3.2. Сборка образа — `docker build`

<mark style="background:#fff88f">Команда создания образа на основе Dockerfile.</mark>

```
sudo docker build -t BEST_SITE:1.0 .
```

<mark style="background:#fff88f">Разбор параметров:</mark>

- <mark style="background:#fff88f">`build` — запуск процесса сборки.</mark>
- <mark style="background:#fff88f">`-t` — назначение имени и тега образа.</mark>
- <mark style="background:#fff88f">`my-nginx` — имя создаваемого образа.</mark>
- <mark style="background:#fff88f">`1.0` — тег образа.</mark>
- <mark style="background:#fff88f">`.` — текущий каталог как контекст сборки.</mark>

Во время сборки Docker последовательно обрабатывает инструкции Dockerfile.

### 3.3. Проверка образа

```
sudo docker images
```

В списке должен появиться образ `my-nginx` с тегом `1.0`.

### 3.4. Запуск контейнера

```
sudo docker run -d --name BEST_SITE -p 8080:80 my-nginx:1.0
```

Проверка:

```
curl http://localhost:8080
```

В результате должна отображаться HTML-страница, добавленная в образ.

## 4. Хранение данных в контейнерах

<mark style="background:#fff88f">После удаления или повторном создании контейнера данные в контейнере будут удалены. Чтобы сохранять данные их нужно хранить вне контейнера. В Docker для этого используются **volumes** — тома, которыми управляет Docker.</mark>

## **6. Docker Volumes**

### **6.1. Понятие Volume**

**Docker Volume** — область хранения данных, управляемая Docker и подключаемая к контейнерам.

Данные тома сохраняются независимо от жизненного цикла контейнера.

Например, можно удалить контейнер с базой данных и создать новый, подключив тот же том. Файлы базы данных останутся доступными.

### **6.2. Создание тома —** `volume create`

```
sudo docker volume create site-data
```

Команда создаёт том с именем `site-data`.

### **6.3. Просмотр томов —** `volume ls`

```
sudo docker volume ls
```

Команда отображает существующие Docker Volumes.

### **6.4. Подключение тома —** `-v`

Для подключения тома используется параметр `-v`.

Синтаксис:

```
-v ИМЯ_ТОМА:ПУТЬ_В_КОНТЕЙНЕРЕ
```

Пример:

```
-v site-data:/data
```

Здесь:

- `site-data` — имя Docker Volume.
    
- `/data` — каталог внутри контейнера.
    

Файлы, записанные контейнером в `/data`, будут храниться в томе `site-data`.

### **6.5. Пример постоянного хранения файлов**

Создание контейнера с подключённым томом:

```
sudo docker run -it --name data-test -v site-data:/data ubuntu:24.04 bash
```

Создание файла внутри контейнера:

```
echo "Hello Volume" > /data/test.txt
```

Проверка содержимого:

```
cat /data/test.txt
```

Выход:

```
exit
```

Удаление контейнера:

```
sudo docker rm data-test
```

Создание нового контейнера с тем же томом:

```
sudo docker run -it --name data-test-2 -v site-data:/data ubuntu:24.04 bash
```

Проверка файла:

```
cat /data/test.txt
```

Файл сохранится, поскольку он размещён в Docker Volume, а не в записываемом слое удалённого контейнера.

### **6.6. Просмотр информации о томе —** `volume inspect`

```
sudo docker volume inspect site-data
```

Команда позволяет получить информацию о томе, включая его имя, драйвер и расположение данных на хосте.

### **6.7. Удаление тома —** `volume rm`

```
sudo docker volume rm site-data
```

Удаление возможно, если том не используется существующими контейнерами.

**Важно:** удаление тома приводит к удалению хранящихся в нём данных.

## **7. Bind Mounts**

### **7.1. Понятие Bind Mount**

**Bind Mount** — подключение существующего файла или каталога хостовой системы внутрь контейнера.

В отличие от Docker Volume, расположение данных определяется администратором.

Например, каталог `/home/user/site` можно подключить к каталогу `/usr/share/nginx/html` внутри контейнера Nginx.

### **7.2. Подключение каталога хоста**

Создание каталога:

```
mkdir -p ~/my-site
```

Создание HTML-файла:

```
echo "<h1>Hello Bind Mount</h1>" > ~/my-site/index.html
```

Запуск контейнера:

```
sudo docker run -d --name bind-site -p 8081:80 -v "$(pwd)/my-site:/usr/share/nginx/html:ro" nginx:stable
```

В этом примере предполагается, что текущий каталог — домашний каталог пользователя, где создан `my-site`.

Разбор:

- `$(pwd)/my-site` — абсолютный путь к каталогу на хосте.
    
- `/usr/share/nginx/html` — каталог внутри контейнера.
    
- `ro` — подключение только для чтения.
    

Проверка:

```
curl http://localhost:8081
```

При изменении HTML-файла на хосте Nginx сможет использовать обновлённое содержимое без пересборки образа.

## **8. Отличия Docker Volume и Bind Mount**

|Характеристика|Docker Volume|Bind Mount|
|---|---|---|
|Управление|Docker|Администратор|
|Расположение|Определяет Docker|Задаётся вручную|
|Основное назначение|Постоянные данные приложений|Подключение файлов хоста|
|Создание|`docker volume create` или автоматически|Использование пути хоста|
|Типичный пример|Данные PostgreSQL|Исходный код и конфигурации|

**Docker Volumes** обычно удобнее для постоянных данных приложений.

**Bind Mounts** удобны, когда необходимо работать с файлами хоста напрямую, например при разработке веб-приложения.
