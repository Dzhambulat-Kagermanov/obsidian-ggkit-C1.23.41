### Что такое SSH

**SSH (Secure Shell)** — протокол для безопасного удалённого управления компьютером по сети. Через него администратор подключается к серверу, запускает команды, передаёт файлы и настраивает сервисы.

SSH шифрует весь трафик между клиентом и сервером. Без шифрования пароли и команды можно было бы перехватить.

SSH работает поверх TCP, по порту **22** по умолчанию.

Компоненты:

|Компонент|Что это|
|---|---|
|`sshd`|Демон (программа) на сервере, принимает подключения|
|`ssh`|Клиент на компьютере администратора|
|`/etc/ssh/sshd_config`|Настройки сервера|
|`~/.ssh/config`|Настройки клиента|
|`~/.ssh/authorized_keys`|Список ключей, которым разрешён вход|
|`~/.ssh/known_hosts`|Список серверов, которым клиент уже доверяет|

### Как устроено подключение

Подключение проходит несколько этапов:

1. **TCP-соединение.** Клиент открывает соединение с сервером на порту 22.
2. **Согласование алгоритмов.** Стороны сообщают, какие алгоритмы шифрования они поддерживают, и выбирают общие.
3. **Обмен ключами (Key Exchange).** Клиент и сервер вычисляют общий секретный ключ сессии. Самое важное здесь: ключ не передаётся по сети. Каждая сторона вычисляет его сама, используя данные, которыми обменялась с другой стороной. Подслушивающий эти данные видит, но вычислить ключ не может.
4. **Проверка сервера.** Клиент убеждается, что подключается именно к нужному серверу.
5. **Аутентификация пользователя.** Сервер проверяет, что вы — это вы.
6. **Сессия.** Открывается оболочка (shell) или передаются файлы. Весь трафик зашифрован.

#### Что такое атака «человек посередине» (MITM)

Представьте, что между вами и сервером стоит злоумышленник. Он перехватывает ваше соединение и выдаёт себя за сервер. Вы отправляете ему пароль, он передаёт его настоящему серверу и получает доступ.

Защита от этого — **хостовый ключ** сервера. У каждого сервера есть уникальный ключ. Клиент запоминает его в `~/.ssh/known_hosts` при первом подключении. Если при следующем подключении ключ изменился, клиент выдаёт предупреждение и отказывается продолжать. Подменить сервер без этого ключа злоумышленник не может.

Проверка выглядит так:

- ключ совпадает — подключение продолжается;
- ключа нет в `known_hosts` — клиент спрашивает, доверяете ли вы этому серверу;
- ключ изменился — **предупреждение о возможной атаке**. Иногда причина безобидна: сервер переустановили. Но сначала нужно выяснить причину.

### Аутентификация пользователя

Сервер должен убедиться, что подключается нужный человек. Есть три способа:

**1. По ключу (`publickey`) — рекомендуемый способ**

У пользователя есть пара ключей: приватный (хранится только у него) и публичный (копируется на сервер). Клиент подписывает запрос приватным ключом, сервер проверяет подпись публичным. Приватный ключ по сети не передаётся.

**2. По паролю (`password`)**

Пароль отправляется внутри зашифрованного канала. Минус в том, что пароль можно подбирать (брутфорс). Ключ подобрать практически невозможно, поэтому парольный вход обычно отключают.

### Как создать ключ?

Ключи создаются командой `ssh-keygen`:

```bash
ssh-keygen -t ed25519 -C "admin@company.ru" -f ~/.ssh/id_ed25519
```

|Алгоритм|Статус|
|---|---|
|**Ed25519**|Рекомендуется. Короткий (256 бит), быстрый, надёжный|
|**RSA 4096**|Допустим для старых систем, которые не понимают Ed25519|
|**DSA**|Устарел и запрещён в современных версиях OpenSSH|
|**ECDSA**|Работает, но вызывает вопросы у специалистов по криптографии|

Для рабочих ключей задавайте **passphrase** — пароль на сам ключ. Если файл ключа украдут, без пароля им не воспользоваться.

Два файла:

- `id_ed25519` — приватный, никому не передаётся;
- `id_ed25519.pub` — публичный, его копируют на серверы.

Публичный ключ на сервер можно передать так:

```bash
ssh-copy-id user@server
```

>[!DANGER] Важно: Права доступа
>SSH откажется работать, если права на файлы слишком открытые. Нужные права:
>```bash
>chmod 700 ~/.ssh                    # директория
>chmod 600 ~/.ssh/id_ed25519         # приватный ключ
>chmod 600 ~/.ssh/authorized_keys    # список разрешённых ключей
>chmod 644 ~/.ssh/id_ed25519.pub     # публичный ключ
>```

### Настройка сервера: `sshd_config`

Файл `/etc/ssh/sshd_config`. Основные параметры:

| Параметр                 | Значение         | Зачем                                                               |
| ------------------------ | ---------------- | ------------------------------------------------------------------- |
| `Port`                   | `22`             | Указать порт по которому работает SSH сервер                        |
| `PermitRootLogin`        | `no`             | Запрет входа под root. Вместо этого — обычный пользователь и `sudo` |
| `PasswordAuthentication` | `yes` / `no`     | Разрешить/Запретить вход по паролю. По умолчанию запрещен           |
| `PubkeyAuthentication`   | `yes` / `no`     | Разрешить/Запретить вход по ключам                                  |
| `MaxAuthTries`           | `3`              | Число попыток входа за одно подключение                             |
| `LoginGraceTime`         | `30`             | Секунд на вход, потом соединение разрывается                        |
| `AllowGroups`            | `ssh-users`      | Войти могут только пользователи указанной группы                    |
После изменений:

```bash
systemctl stop ssh.socket
systemctl disable ssh.socket
systemctl enable --now ssh.service
```

**Перед перезапуском sshd не закрывайте текущую сессию.** Если ошибиться в настройках, именно открытая сессия позволит откатить изменения. Иначе можно потерять доступ к серверу.

### Файл `authorized_keys`

В нём перечислены публичные ключи, которым разрешён вход. Каждый ключ на отдельной строке:

```
ssh-ed25519 AAAAC3Nza... alice@company.ru
ssh-ed25519 AAAAC3Nza... bob@company.ru
```

Перед ключом можно поставить **опции**, которые ограничивают его:

```
from="10.0.0.0/8" ssh-ed25519 AAAA... admin@company.ru
command="/usr/local/bin/backup.sh" ssh-ed25519 AAAA... backup-bot
no-port-forwarding,no-pty ssh-ed25519 AAAA... monitor
```

| Опция                | Что делает                                          |
| -------------------- | --------------------------------------------------- |
| `from="..."`         | Разрешает вход только с указанных адресов           |
| `command="..."`      | Всегда запускает одну команду, а не открывает shell |
| `no-port-forwarding` | Запрещает туннели                                   |
| `no-pty`             | Запрещает интерактивный терминал                    |

Опция `command` удобна для служебных ключей. Например, ключ для резервного копирования может запускать только скрипт бэкапа и ничего больше.

### Настройка клиента: `~/.ssh/config`

Вместо длинной команды вида `ssh -i ~/.ssh/key_prod -p 2222 deploy@10.0.0.5` можно описать сервер в конфиге:

```
Host prod-web
    HostName 10.0.0.5
    User deploy
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_prod
    IdentitiesOnly yes
```

Теперь достаточно написать:

```bash
ssh prod-web
```

Директива `IdentitiesOnly yes` говорит клиенту использовать только указанный ключ. Без неё клиент перебирает все ключи подряд, и сервер может отказать из-за слишком большого числа попыток.

### Безопасность: что настроить в первую очередь

Меры по убыванию важности:

1. **Запретить вход root** (`PermitRootLogin no`).
2. **Запретить вход по паролю** (`PasswordAuthentication no`). Сначала убедитесь, что ключ работает.
3. **Ограничить круг пользователей** (`AllowGroups` или `AllowUsers`).
4. **Защита от перебора паролей.** Утилита **fail2ban** блокирует IP-адреса после нескольких неудачных попыток. Альтернатива — `pam_faillock`.
5. **Двухфакторная аутентификация** для привилегированных доступов.
6. **Файрвол.** Открыть порт SSH только для нужных адресов.
7. **Смена порта.** Снижает количество автоматических сканирований, но не защищает от целенаправленной атаки. Это не замена остальным мерам.

#### Что такое брутфорс

Брутфорс — подбор пароля перебором. Боты пробуют тысячи логинов и паролей на каждом открытом SSH-сервере. Поэтому вход по паролю опасен: пароль можно подобрать, а ключ — практически нет.

### Передача файлов

**SCP** — копирование файлов одной командой:

```bash
scp file.txt user@server:/tmp/
scp user@server:/var/log/app.log ./
```

### Диагностика частых ошибок

|Ошибка|Частая причина|Что сделать|
|---|---|---|
|`Connection refused`|sshd не запущен или порт закрыт|`systemctl status sshd`, проверить файрвол|
|`Connection timed out`|Нет сетевого доступа|`ping`, `nc -zv server 22`|
|`Permission denied (publickey)`|Ключа нет на сервере, неверные права, неверный пользователь|Проверить `authorized_keys`, права, логин|
|`Host key verification failed`|Изменился ключ сервера|Выяснить причину, затем удалить строку из `known_hosts`|
|`UNPROTECTED PRIVATE KEY FILE`|Приватный ключ доступен другим пользователям|`chmod 600` на файл ключа|
|`Too many authentication failures`|Клиент перебрал слишком много ключей|`IdentitiesOnly yes` в `config`|

Подробный вывод для диагностики:

```bash
ssh -vvv user@server
```

Логи на сервере:

```bash
tail -f /var/log/auth.log | grep sshd    # Debian/Ubuntu
tail -f /var/log/secure | grep sshd      # RHEL/CentOS
```
